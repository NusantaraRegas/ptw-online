## Keputusan yang dibutuhkan

- Dimensi dan hasil matriks risiko yang disahkan.
- Reviewer wajib per kelas/risk/location serta otoritas keputusan final.

## Keputusan

### Input bisnis untuk flow utama

Input berikut telah dikonfirmasi untuk implementasi MVP, tetapi record tetap `DRAFT` sampai owner,
approver, referensi keputusan, dan policy version dilengkapi:

Input berikut mengikuti BRD v1.8 (DEC-118 sampai DEC-123) dan sistem yang berjalan per
22 September 2026:

- Kontraktor/User Sponsor (role `Sponsor`) mengajukan PTW dengan dokumen dasar lengkap.
- Submit membentuk tepat satu task `HSE_VALIDATION` secara atomik untuk versi PTW yang sama. Hanya
  PIC HSE (role `HSEValidator`) yang memvalidasi dan sekaligus menetapkan Bagian 5; Sponsor tidak
  boleh memvalidasi PTW miliknya sendiri.
- Setelah validasi valid, sistem membentuk tepat satu task `AREA_OPERATION_REVIEW` untuk pool
  SO/Officer pemilik wilayah (role `AreaOwnerSeniorOfficer`, area-scoped). Reviewer pertama yang
  menyelesaikan task menetapkan checklist kondisi operasi Bagian 7; Sponsor dan validator HSE tidak
  boleh menjadi reviewer.
- Setelah review Bagian 7 selesai, sistem membentuk tepat satu task `AREA_APPROVE_AND_ISSUE` untuk
  Manager pemilik wilayah (role `AreaOwnerManager`, area-scoped). Manager menyetujui **dan**
  menerbitkan dalam satu command atomik; tidak ada command penerbitan terpisah dan tidak ada status
  `OPEN`. Manager harus berbeda dari Sponsor, validator HSE, dan reviewer SO/Officer.
- Permintaan revisi atau penolakan dapat dilakukan oleh PIC HSE pada task validasi, SO/Officer pada
  task review, dan Manager pada task approval; alasan wajib. Revisi membatalkan task tertunda,
  menghapus evidence Bagian 5/7 versi tersebut, dan membentuk notifikasi task `SPONSOR_REVISION`
  kepada Sponsor; submit ulang menaikkan versi PTW.
- Routing pemilik wilayah rilis awal: ORF ke Distribusi Gas dan Pengelolaan ORF; Site Office ke
  General Affair; Water-Based Activity ke Transport & Operasi FSRU (DEC-116). HO dan FSRU tidak aktif.
- PIC HSE atau Manager pemilik wilayah dapat menangguhkan PTW Diterbitkan seketika dengan alasan;
  Manager pemilik wilayah menyelesaikan penangguhan dan PTW kembali `ISSUED`.
- Tidak ada `WORK_COMPLETED` atau konfirmasi digital tiga pihak. Sponsor mengajukan penutupan dengan
  hardcopy final yang cocok dengan paket cetak resmi; Manager pemilik wilayah memverifikasi Bagian 10
  secara terstruktur lalu menutup, atau meminta tindak lanjut. PIC HSE tidak memiliki task close.
- Sponsor pemilik mengajukan renewal dari PTW `ISSUED`/`EXPIRED` dengan hardcopy hasil verifikasi
  lapangan; Manager pemilik wilayah meninjau (`AREA_RENEWAL_REVIEW`) dan draft penerus baru dibuat
  hanya setelah approval, lalu mengikuti workflow normal dari awal (lihat PTW-RENEWAL).
- Approval sebagai pejabat pengganti (`ActingAssignmentId`) ditolak sampai model penugasan pengganti
  lengkap dan disahkan melalui record ini.

Profil role Development (`UserAuthorizationRoleProfiles` pada `appsettings.Development.json`)
menurunkan action code per role di server untuk keperluan UX/UAT dan **bukan** matriks produksi. Nama
posisi SO/Officer dan Manager konkret per wilayah, kompetensi, dan assignment produksinya tetap harus
ditetapkan melalui konfigurasi effective-dated serta pengesahan policy.

## Acceptance dan bukti UAT minimum

- [ ] Seluruh role/action memiliki owner, scope, effective period, dan competency requirement.
- [ ] Matriks risk/class/location menghasilkan tepat satu route dan final authority atau DENY eksplisit.
- [ ] Validasi PIC HSE tunggal, review Bagian 7 SO/Officer, dan approve-and-issue Manager pemilik
      wilayah disahkan secara formal beserta nama posisi per wilayah.
- [ ] Pasangan SoD dan pengecualian dinyatakan per action/konteks, bukan larangan multi-role global.
- [ ] Delegasi tidak dapat memperluas source authority dan memiliki batas akhir serta alasan.
- [ ] Assignment/kompetensi hilang, kedaluwarsa, ambigu, atau berubah di tengah workflow memiliki
      expected outcome fail-safe.
- [ ] Paket UAT mencakup ALLOW, missing assignment, expired assignment, missing competency,
      ambiguous assignment, multi-role valid, SoD conflict, delegation boundary, dan stale version.
- [ ] Passing UAT report memakai policy version yang sama dengan decision record.
- [ ] HSE dan Operasi mencatat referensi SOP/notulen, approver, dan tanggal efektif.

## Usulan implementasi framework untuk divalidasi

Usulan berikut sudah diwujudkan sebagai framework decision-neutral, tetapi **belum merupakan
kebijakan produksi**:

- satu karyawan boleh memiliki lebih dari satu assignment role yang efektif pada saat bersamaan;
- separation of duties dievaluasi terhadap actor, action, permit/konteks, dan tahap keputusan,
  bukan dengan melarang multi-role secara global;
- pembuat atau pengaju assignment tidak boleh menjadi checker assignment yang sama;
- delegasi harus memiliki sumber assignment langsung yang telah disetujui, penerima berbeda,
  periode akhir terbatas, dan scope role/action/kompetensi/lokasi/periode yang tidak lebih luas dari
  sumbernya;
- assignment yang belum disetujui, belum efektif, atau kedaluwarsa tidak memberi authority;
- tidak adanya assignment atau lebih dari satu assignment role yang ambigu untuk action dan konteks
  yang sama menghasilkan penolakan fail-safe.

Daftar role/action resmi, pasangan SoD per transition, rute approval, kompetensi, dan pengecualian
tetap harus disahkan oleh owner OPN-002 sebelum activation gate command PTW boleh dinyalakan.

Activation gate opt-in (`OperationalPolicy:EnforceMasterAuthorization`) tersedia untuk seluruh command
PTW: create/update/submit/cancel draft, validasi, eskalasi, review Bagian 7, approve-and-issue,
revisi/penolakan, suspend/resolve, renewal, closure, dan expire. Gate tidak membawa daftar action
default: deployment wajib memasukkan mapping `PermitActionCodes` dan `AcceptedDecisionReferences` dari
keputusan yang telah disahkan. Ketika aktif, assignment atau competency evidence yang
hilang/kedaluwarsa/ambigu ditolak dan bukti keputusan dicatat ke audit permit. Enforcement tetap
nonaktif selama record ini `DRAFT`; Development memakai profil role sebagai pengganti sementara.

Assignment role langsung (`POST /api/v1/admin/authorizations/direct`) hanya menerima pengguna, role,
area bila role area-scoped, dan periode; action code serta kompetensi diturunkan server dari profil
role. Tanpa profil terkonfigurasi, jalur ini fail-closed.

Simulator non-authoritative tersedia pada `/admin/policy` untuk memvalidasi skenario actor, action,
lokasi, periode, multi-role, dan kompetensi sebelum keputusan diterima. Outcome simulasi tidak
mengubah data dan tidak merupakan approval atau izin kerja.

Paket UAT immutable dan berversi tersedia pada `/admin/policy-uat`. Administrator dapat membekukan
expected outcome, menjalankan batch simulator, lalu menyimpan coverage dan checksum report sebagai
evidence. Activation gate mensyaratkan passing run untuk policy version yang sama persis, tetapi
passing run bukan pengesahan record ini: status tetap `DRAFT` sampai owner dan approver memberi
referensi keputusan resmi.
