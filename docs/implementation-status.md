# Status implementasi BRD/PRD/FSD v1.8

Tanggal pemeriksaan: 24 September 2026. Dokumen requirement v1.8 diperlakukan sebagai sumber kebutuhan; keputusan OPN-001–012 yang belum disahkan tidak diberi nilai bisnis fiktif.

BRD/PRD/FSD v1.8 (diperbarui 24 September 2026) menggantikan v1.7 dan menyelaraskan requirement dengan flow yang sudah berjalan: review Bagian 7 oleh SO/Officer pemilik wilayah sebelum approval Manager, pembagian pengisian Bagian 1–7 (Sponsor 1–4, PIC HSE 5, SO/Officer dan Manager 7), dokumen dasar JSA/Prosedur Pekerjaan/ID/BPJS TK/FTW/E-SIMI, renewal berbasis review pemilik wilayah, closure dengan verifikasi Bagian 10, notifikasi revisi Sponsor, paket cetak dua halaman A3, dan identitas lokal Development. DEC-127 menetapkan Prosedur Pekerjaan sebagai checklist wajib Bagian 4 yang otomatis terpilih dan dicetak. Keputusan baru tercatat sebagai DEC-117 sampai DEC-127 pada BRD v1.8; ID requirement pada tabel di bawah mengacu pada penomoran v1.8.

## Migration baru

1. `20260915072103_AlignPermitLifecycleV16`
   - memetakan status legacy secara konservatif;
   - menormalkan `HSSE_VALIDATION` menjadi `HSE_VALIDATION`;
   - membatalkan task gas dan task workflow legacy;
   - membentuk task atomik `AREA_APPROVE_AND_ISSUE` untuk permit in-flight;
   - menambahkan decision, immutable print snapshot, dan generated document queue.
2. `20260915074426_AddV16AttachmentEvidenceMetadata`
   - menambahkan category, nomor/revisi/tanggal dokumen, target PermitVersion, PrintPackage, dan supersedes lineage;
   - mengubah status legacy `NOT_SCANNED` menjadi `PENDING`;
   - menambahkan FK, check constraints, dan indexes.
3. `20260915081658_AddMalwareScanEvidence`
   - menambahkan referensi evidence dan timestamp scan;
   - mewajibkan evidence untuk setiap status `CLEAN` melalui check constraint;
   - menurunkan status `CLEAN` legacy tanpa evidence menjadi `PENDING` secara fail-closed.
4. `20260915105217_AddPrintPackageRendererVersion`
   - menambahkan `RendererVersion` pada `doc.GeneratedDocument` agar setiap file resmi dapat ditelusuri ke build renderer yang menghasilkannya.
5. `20260916145609_AddSupportingDocumentAttachmentCode`
   - menambahkan kode dokumen Bagian 4 nullable pada setiap lampiran agar file dapat direkonsiliasi dengan checklist resmi;
   - menambahkan index aktif per permit/kode tanpa mengubah atau menghapus data lampiran lama.
6. `20260921190541_BackfillSponsorRevisionTasks`
   - membuat task `SPONSOR_REVISION` yang ditugaskan langsung kepada Sponsor untuk PTW existing berstatus `RevisionRequired` yang belum memiliki task tersebut;
   - menambahkan audit dan outbox rekonsiliasi tanpa mengubah status atau versi PTW.
7. `20260922030206_AddDemoModeSetting`
   - menambahkan tabel `cfg.DemoModeSetting` (satu baris, `Version` > 0, `rowversion`) untuk pengaturan mode demo persisten;
   - menambahkan tabel `intg.DemoModeCommandReceipt` dengan index unik actor/operation/key untuk idempotency command enable/disable.
8. `20260922073129_SeparatePermitBusinessRevision`
   - menambahkan `Permit.BusinessVersion` dan tabel snapshot `ptw.PermitRevision`, sehingga versi bisnis terpisah dari sequence perubahan legacy;
   - merekonsiliasi PTW existing berdasarkan jumlah event submit: pengajuan awal tetap v1 dan setiap submit ulang menambah tepat satu versi;
   - mempertahankan nilai versi lama pada kolom `Legacy*`, menyelaraskan task, decision, paket cetak, dan lineage lampiran, serta menambahkan audit/outbox rekonsiliasi;
   - memperbolehkan lampiran ditambahkan dan dibatalkan dalam revisi bisnis yang sama tanpa membuat versi PTW fiktif.
9. `20260922074402_ReconcilePermitBusinessVersions`
   - guard idempotent untuk menyelesaikan rekonsiliasi pada database yang sudah menerima schema versi bisnis sebelum backfill selesai;
   - tidak mengubah database yang sudah konsisten dan tetap menghasilkan audit/outbox ketika rekonsiliasi diperlukan.
10. `20260922075901_PreserveLegacyPermitVersionLineage`
   - menambahkan kolom versi bisnis tersendiri pada task, decision, paket cetak, dan lampiran;
   - mempertahankan kembali nomor lineage lama pada record serta snapshot paket cetak immutable, sementara API dan workflow memakai versi bisnis;
   - tidak merender ulang atau mengganti PDF `READY`; perubahan lineage dicatat melalui audit dan outbox.

Migration bersifat additive/forward dan mempertahankan kolom legacy `ActiveWorkPeriodId` sebagai compatibility column yang tidak lagi dipakai journey aktif. Penghapusan fisiknya memerlukan tahap contract migration terpisah setelah verifikasi data.

## UAT manual increment lifecycle

1. Jalankan stack Development dan migration pada database kosong.
2. Sebagai Sponsor, buat draft ORF, Site-Office, dan Water-Based Activity. Pastikan JSA dan Prosedur Pekerjaan otomatis terpilih serta tidak muncul sebagai checkbox opsional Bagian 4; pastikan keduanya bersama ID, BPJS TK, FTW, dan E-SIMI tampil sebagai dokumen dasar wajib. Setelah lengkap, pastikan masing-masing hanya membuat satu task `HSE_VALIDATION`.
3. Coba validasi dengan identity Sponsor yang sama dan pastikan ditolak; validasi dengan PIC HSE lain, pilih minimal satu APD/perlengkapan safety Bagian 5, lalu pastikan pilihan tersimpan, tampil memakai nama katalog pada detail PTW tanpa mengekspos kode API, dan muncul sebagai centang pada paket cetak. Coba kirim pilihan kosong atau kode di luar katalog dan pastikan ditolak.
4. Sebagai SO atau Officer pemilik wilayah yang scope-nya cocok, buka task `AREA_OPERATION_REVIEW`, pilih kondisi operasi Bagian 7 beserta subpilihan yang diwajibkan, isi komentar keputusan, lalu sahkan. Pastikan komentar kosong/spasi mengunci tombol, Manager belum menerima task sebelum langkah ini, actor Sponsor/PIC HSE ditolak oleh SoD, hanya reviewer pertama yang berhasil, dan setelahnya tepat satu task `AREA_APPROVE_AND_ISSUE` dibuat.
5. Sebagai Manager pemilik wilayah yang scope-nya cocok dan actor-nya berbeda dari reviewer SO/Officer, jalankan `approve-and-issue`; pastikan Manager wilayah lain ditolak, lalu verifikasi status **Diterbitkan**, dua decision (review SO/Officer dan approval Manager), audit, outbox, snapshot, dan generated document `PENDING`.
6. Ulangi command dengan key/payload sama dan pastikan hasil pertama dikembalikan; ubah payload dengan key sama dan pastikan `409`.
7. Uji request revision dan reject dari HSE/Manager: komentar wajib diisi, alasan tampil pada riwayat PTW, evidence/task lama batal untuk revisi, dan submit ulang membuat task baru. Pastikan pula komentar validasi HSE, review SO/Officer, dan approval Manager tampil pada ringkasan workflow detail PTW.
8. Uji submit HO dan FSRU lalu pastikan `permit.location.not_released`; pastikan ORF, Site-Office, dan Water-Based Activity dapat melanjutkan workflow.
9. Uji suspend langsung dan resolve; pastikan UI tetap memperingatkan revalidasi hardcopy.
10. Unggah signed field copy terbaru yang `CLEAN` dan cocok dengan exact PrintPackage/PermitVersion. 11. Unduh paket cetak setelah status berubah menjadi `READY`. Verifikasi Bagian 3 berisi nama lengkap, jabatan, departemen, exact PNG signature Sponsor, dan waktu submit; tanda tangan Pelaksana Pekerjaan tetap kosong. ## Risiko yang memblokir produksi

Topologi, identitas, dan kebijakan unggahan produksi telah disahkan (OPN-007, OPN-009, PROD-UPLOAD-SCAN) dan `compose.prod.yaml` dapat dijalankan. Risiko yang tetap terbuka: authorization acting/owner yang belum lengkap (OPN-001/002; produksi berjalan dengan `EnforceMasterAuthorization=false` dan profil role yang sama dengan Development), E-SIMI/contractor identity belum ada, UAT operasional closure belum disahkan, retensi dan RPO/RTO eksplisit (OPN-008), observability/on-call, unggahan tanpa scanner (risiko diterima), tidak ada HA dan tidak ada perlindungan DDoS volumetrik di depan nginx, serta batas kapasitas SQL Server Express. Paket cetak sudah dihasilkan, tetapi kesetiaan tata letak terhadap formulir terkontrol wajib diverifikasi dan disahkan HSSE sebelum dipakai di lapangan.
